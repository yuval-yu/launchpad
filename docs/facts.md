# 什么进索引层，什么留在 Java

这是整套设计里唯一需要反复判断的问题。代价不对称：**口径误进了 Envio handler，改一次口径就要重跑整条链**， HyperSync 上是分钟级，但每次都要重新部署并等它追上；口径留在 Java，改了只是重算一张表。所以拿不准的时候往事实那边放， 还有一条推论：**凡是将来可能成为口径的维度，事实要拆开存，不要提前合并**。

## 判据表

| Envio · 事实、机械派生、成交时点 USD | Java · 业务口径、现价类 USD |
|---|---|
| 某区块某地址用 `1.5e18` quote 换走 `98931e18` token，其中 fee `x`、tax `y`；按那一分钟的 WETH 价折成 `$4200` | 这笔算「买入」、计入成交额、成交额含不含 tax |
| 这笔成交发生在曲线上还是毕业后的池子里 | 「24h 成交额」「协议成交额」算不算 DEX 那部分。**所以累加值和桶里曲线量、池子量分开存** |
| 该币的 curve 合约在某区块关闭了 | 这个币的状态是「已毕业」。「曲线一关就算毕业」是产品口径，不是链上概念，链上关曲线和建池是两步，见下一节 |
| 地址 X 持有该币 `1000e18`，正余额地址共 842 个 | X 算不算「持有人」：要剔除 curve、PoolManager、锁仓合约，剩下的才是展示的持有人数 |
| 该币最后一笔成交价是 `0.0000412` WETH；净募集 `3.2e18` | 现在值多少美元、市值多少、流动性多少：**要乘此刻的 WETH 价**，ETH 一动全表都变，只能 Java 定时算 |
| 发币事件里 `socials.storyFun` 与 `website` 的原文、`creator` 地址 | 发行者对应哪个平台用户、`storyFun` 路径绑到哪部剧、OG 是谁 |
| 按分钟 / 小时 / UTC 日机械分桶的原始量、开高低收及各自的 USD | 滚动 24h、五档 K 线各用哪个桶、颗粒多细、空档补不补。**分桶粒度是机械的，用哪一档才是口径** |
| 合约锁掉了多少供应（`lockedSupply`） | 流通量算不算曲线里的币。**口径：流通量恒等于总供应**，锁仓量只存不用 |

## 举个例子：「曲线关了」和「已毕业」为什么不是一回事

上表第三行最容易被读成废话，展开说一次。

链上的毕业不是一步，是两步，中间还可能失败。合约里一个币有四个状态：

| 合约状态 | 发生了什么 | 触发事件 |
|---|---|---|
| `Trading` | 曲线上正常买卖 | TokenLaunched |
| `Swept` | 曲线卖完了，`closeCurve` 把储备收进工厂。**曲线关闭、不能再交易，但池子还没建** | LaunchSwept |
| `Graduated` | 有人调了 `graduate`，储备交给 Receiver，Uniswap v4 池建好、流动性永久锁定。**这时才能在池里交易** | V4PoolGraduated |
| `Rescued` | 卡在 Swept 超过 7 天没建成池，治理把储备释放走。**永远不会有池** | LaunchGraduationRescued |

Swept 到 Graduated 通常是同一笔或紧接着的一笔交易，但合约允许它们分开，允许第二步失败重试，也允许走到 Rescued。 所以索引层记的是三个**时间戳**：`curveClosedAt`、`poolCreatedAt`、`rescuedAt`，每一个都是链上事实。

**「曲线一关就算毕业」是现行展示规则**：收到 LaunchSwept 就把币标成 GRADUATED、挪到已毕业分区。选这一步而不是等池建好，是因为对用户来说曲线已经买不到了，留在「进行中」分区会误导，而池子通常几秒后就有。 但它是个选择，不是唯一答案：也可以等 V4PoolGraduated 再标毕业、Swept 期间显示「毕业中」，或者三个时间戳都给前端。

::: tip
这就是为什么「已毕业」这个词不能写进 handler。索引层只负责三个时间戳，哪个时间戳一到就翻成 GRADUATED 是 Java 线二的一行代码，产品改主意只改那一行，索引不用重跑。

**Rescued 的问题由此而来**：币在 Swept 时已显示「已毕业」，之后走到 Rescued 就成了挂着毕业徽标却没有池的币。展示口径见[第 1 页](/) TODO。
:::

## USD 的两类，只有一类进索引层

| 类型 | 例子 | 放哪 | 为什么 |
|---|---|---|---|
| **成交时点固化** | 每笔成交的 `amountUsd`、每个桶的 `openUsd…closeUsd` 与 `volumeUsdCurve / volumeUsdPool`、协议日的两列 USD 成交额 | **Envio handler** | 乘的是那一刻的价，写下就不该再变；handler 按区块时间从价格历史取，重跑结果确定，重组时随实体回滚 |
| **跟着现价走** | 现价、市值、流动性、24h 成交额、24h 涨跌 | **Java 线二 / 线三** | ETH 一动全表都要变，而 Envio 的实体只在该币下一笔成交时才重写，不活跃的币会停在旧价上。这一类正是市场列表的排序键 |

## 为什么这条线必须划得这么保守

::: warning
看看我们这几个月真实改过的口径：滚动 24h 改成昨天这个完整 UTC 日、市值口径从 ETH 改回 USD、 持有者榜剔除合约的判据、OG 徽标怎么算、日视图基线取哪天、成交额缺失时给 null 还是回落。 **全是口径。链上事实一次都没变过。**

handler 里只写解码后的原始参数、纯加减的派生和「按区块时间取价相乘」这一条固定规则，上面这些改动就都只是 Java 重算，索引层一次都不用重新部署。
:::

## Envio 里明确不做的

| 不做 | 因为 | 交给谁 |
|---|---|---|
| **现价类 USD** | 见上表 | Java 线二 / 线三 |
| **`GRADUATED` 等状态名** | 存时刻不存状态名 | Java 线二 |
| **`holderCount` / `deployerHoldingPct`** | 剔哪些合约是业务判断。Envio 只给「正余额地址数」和每个地址的余额 | Java 线二 |
| **滚动 24h 值** | 成交滑出窗口不触发任何事件，存了就是挂着旧值永不归零 | Java 线三 |
| **叙事绑定、OG、发行者是哪个平台用户** | 要查 `drama` 和 `user_wallet_address` 表，是平台语义 | Java 线二 |
| **任何 Transfer 明细** | 没有读者：交易者归属在 Transfer handler 里当场回填，回滚由 Envio 做。数据量最大，不建 | handler 只更新 Balance |
| **配对资产的余额** | 要追全链所有 WETH / USDG 持有者，事件量是发射台自己的几十倍，而资产页只要一个地址的几个数 | Java 读时 RPC `balanceOf` |

**两个进了索引层的口径。** 一是**池内成交的交易者**：Activity 要按交易者查，交易者必须是 Envio 里的字段，曲线成交用 `recipient` / `initiator`，池内成交由同一笔 tx 里随后的 Transfer handler 回填 `trader`。 二是**持仓成本法**：移动平均，每笔卖出结一笔已实现盈亏，维护在 `Position` 与卖出那笔 `Trade` 上。两条都是按地址列一批、要分页的读路径逼出来的；规则改了要重跑索引，接受（见[第 4 页](/indexer)）。
